HRX Loom

Model optimization outside the inference engine — on Strix Halo

A model package, not an engine patch.

Historically, supporting a new architecture meant changing the inference engine and waiting on its maintainers. Loom moves the model's structure, tensor layouts and numerical implementations into a package that the server loads. The thing a porter edits is the package — never the runtime.

three commandsverified with hrx-loom 0.2.0 on Strix Halo
install
$ pip install 'hrx-loom[hf]==0.2.0'

Compiler, runtime and loom-serve. The 0.2.0 wheel is about 20 MB.

fetch
$ loom-fetch --preset=chat --output=<dir> https://huggingface.co/loom-fun/<pkg>/resolve/main/model.json

Pulls the package and the upstream GGUF from its original repo, verifying sha256. The GGUF is never re-hosted.

serve
$ loom-serve --model=<dir>/model.json --device=amdgpu

OpenAI-style chat API on 127.0.0.1:8080 (change with --listen). Emits {"event":"ready","address":"127.0.0.1:8080","models":1}.

The port is driven by an agent, and it has to show its work.

loom-skills gives a coding agent nine skills and a four-stage loop. The interesting part for us is not that an agent writes kernels — it is that the loop refuses to report a number that has no evidence behind it.

1

Port

loom-port-llm/port.sh

Reuses existing work, builds the model package, tests basic behaviour.

→ a model served locally
2

Measure

qualify.sh

Runs the validation gates, takes a llama.cpp ROCm baseline, computes a roofline to decide what is even reachable.

→ a baseline and a realistic target
3

Optimize

within the roofline budget

Tries changes, measures each, re-checks correctness. Defaults to a 30-minute budget; you can set your own target instead.

→ the best verified build found
4

Report

finalize.sh

Full gates, audit, and a report. The model card is generated from the run's own logs — a value with no evidence renders as not measured.

→ a package others can re-run
the roofline step is the honest one

Before optimizing, the agent estimates the performance limit and tells you if your target is out of reach. That is what stops the loop from burning a long budget (say, the 3 hours in the last example below) chasing a number the memory system cannot deliver.

> /loom Port, validate and optimize <hf-gguf>. > /loom … until decode is 50% faster than llama.cpp. > /loom … for 3 hours.

The agent runs unattended except to accept a gated model's licence.

    The bottleneck that moved.

    Fifty models across eighteen architectures in three to four days, as reported by Phoronix (the published catalog has since grown to 51). That timeline is the project's account, not something this demo measured. The number worth arguing about internally is not the speedup — it is the elapsed time, and what it implies about who is allowed to add a model.

    before
    • New architecture → patch the inference engine
    • Change lands in the engine's release cycle
    • A small group of maintainers is the throughput limit
    • Niche and new models wait, or never arrive
    • Optimization is coupled to the server you run
    with Loom
    • New architecture → author a model package
    • Register, unregister or swap it over HTTP without restarting the server
    • Anyone with the SDK and a GPU can port and publish
    • A port is shareable source, not a vendor patch
    • A better decoder or quantization carries to the next port
    validation gates across the catalog

    A port is only as good as what it is checked against. Each package is graded on up to thirteen gates, most comparing generated tokens directly with llama.cpp.

    what this demo does not show
    • No local measurement unless you connect one. In replay mode every figure is published loom-fun data from 2026-11-13, not a reading from the machine in front of you.
    • The catalog snapshot predates hrx-loom 0.2.0. The 2026-11-13 data was captured before the loom-fun cards were promoted to 0.2.0 (2026-11-16/17); current cards may show different figures.
    • No power, thermal or memory-pressure data. The catalog does not publish it, and on a 128 GB Strix Halo part that is a real question this demo cannot answer.
    • No cold-start or compile-time figures. "Kernels compile in microseconds to milliseconds" is the project's claim, not something measured here.
    • One llama.cpp baseline. Comparisons use the ROCm backend at the build recorded per model. The published catalog carries no Vulkan numbers; on the model cards, Vulkan is usually the faster llama.cpp backend for decode and the slower one for prefill.
    • Tech preview. HRX Loom is labelled a tech preview by AMD. Nothing here should be read as a product commitment.
